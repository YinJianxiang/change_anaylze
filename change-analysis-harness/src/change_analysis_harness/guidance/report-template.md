# Test scope report template

## 分析范围

- 模式：Mode A（仅代码变更）/ Mode B（需求对照）
- 变更来源：工作区 / 暂存区 / commit / range / PR / patch
- 覆盖范围：已深入检查的模块
- 未覆盖：未读取、被截断或无法验证的内容

## 仓库上下文

- 分析模式：Full repository context analysis / Diff-only analysis
- 仓库来源：现有本地仓库 / 临时克隆 / 临时 worktree / 仅 patch
- PR 编号：
- base SHA：
- head SHA：
- merge base：
- PR 信息来源：gh / GitHub API / Git ref / 用户提供
- 完整搜索调用链：是 / 否
- 候选源码文件 / 已扫描源码文件：
- 轻量级调用图：定义数 / 调用点数 / 调用边数
- 全项目源码扫描完成：是 / 否；若否，说明超时、上限、解析失败或截断
- 未解析的 Symbol：
- 未深入检查的文件：

Diff-only 时必须写明：`未获取完整仓库，无法确认所有间接调用方和完整回归范围。`

## 改动与需求摘要

- 代码事实：有直接证据的行为变化
- 需求推断：仅 Mode A，附置信度
- 需求结论：Mode B，回答需求是否全部实现；汇总验收点总数及已实现、部分实现、未实现、实现与需求不一致、无法确认、不适用的数量。尚有未核验内容时不得宣称全部实现；源码实现与运行验证分开。

## 回归范围

- 核心回归：与改动共享入口、状态、接口或数据的流程
- 定向回归：具体消费者和相邻边界
- 可不回归：仅在有明确隔离证据时列出

## 需求追踪（仅 Mode B）

| 需求 ID | 验收点 | 实现证据 | 测试证据/建议 | 状态 |
|---|---|---|---|---|

从完整需求拆分并编号所有可独立判断的验收点，每点一行，包括本次 diff 未涉及的要求；必要时定向检查目标版本已有代码、前后端、配置和数据脚本。需求原文位置写入验收点，实现证据给目标版本文件/行号，注明本次新增或已有实现。

状态统一为：已实现 / 部分实现 / 未实现 / 实现与需求不一致 / 无法确认 / 不适用。部分实现列明缺失分支；未实现需有应承载位置与实际缺失证据，不能仅凭无 diff 或搜索零命中判定。无法访问的仓库、图片/原型、关联文档或缺少业务口径标为无法确认并列限制；不适用需有明确范围依据。

缺失或不一致项写明需求预期、实际行为、业务影响和对应测试建议，并关联必测内容。没有执行的测试不能写通过。所有已识别验收点必须有状态；未读取的需求内容单列缺口，不能以表格有行就认定完整覆盖。

### 疑似超范围实现

列出没有需求依据的用户可见行为或高风险技术变更，并说明判断证据。

## 建议执行

列出仓库中实际存在的测试文件或命令。未执行时明确写“未执行，仅建议”。

## 待确认与限制

- 待确认：会改变测试预期或发布决策的问题
- 分析限制：缺失需求、动态配置、外部系统、截断 diff 等
