# 影响分析和测试点指南

> 本文是 Codex 读取 Harness 证据后的分析指南，不是 Harness 的扫描算法。Harness 不执行全仓库通用分析。
> 小节使用 `<!-- section:id -->` 标记，供 ImpactUnit 按文件类型切片加载。

<!-- section:evidence-priority -->
## 证据优先级

1. Git diff 和变更行。
2. `java_ast.changed_scopes` 和 `calls_from_changed_scopes`。
3. 变更文件源码。
4. `caller_candidates`、`symbol_references`、`api_references` 等定向搜索结果。
5. 命名和经验推断。

第 1-3 类可作为直接证据。第 4 类是候选证据，必须查看源码后才能确认。第 5 类必须标记为推断或待确认。

<!-- section:impact-steps -->
## 影响分析步骤

1. 从需求中提取功能、验收、边界和兼容性要求。
2. 从 Java AST 变更作用域确定实际变更的类、方法和构造器。
3. 检查变更作用域内的下游调用。
4. 使用定向引用候选反向确认入口、上游调用方和相关测试。
5. 确认接口、数据库、配置、定时任务、消息和外部依赖是否实际受影响。
6. 建立“需求 -> 实现证据 -> 影响路径 -> 测试点”追踪。

<!-- section:risk-levels -->
## 风险等级

- P0: 资金、权限、数据丢失、严重安全问题或核心业务不可用。
- P1: 核心流程、公共接口、事务、并发、历史数据或大范围公共方法风险。
- P2: 有限范围的业务逻辑、配置、校验、缓存或兼容性风险。
- P3: 局部优化、文案、低影响重构或建议项。

<!-- section:api -->
## API 与接口兼容

关注 Controller / API DTO 变更时：

- 请求/响应字段增删、类型变更、默认值和空值语义。
- 鉴权、限流、幂等和错误码是否变化。
- 旧客户端兼容路径与灰度开关。
- 接口级测试与契约/联调验证。

<!-- section:sql -->
## SQL 与事务

关注 Mapper / DAO / SQL 变更时：

- WHERE/JOIN/聚合条件是否改变结果集。
- NULL 处理、分页、排序和历史数据兼容。
- 事务边界、锁粒度和幂等写入。
- 与物化视图、ETL、同步任务的联动。

<!-- section:config -->
## 配置与开关

关注配置文件或 Config 类变更时：

- 默认值、环境差异和回滚方式。
- 功能开关打开/关闭两条路径。
- 配置错误或缺失时的降级行为。

<!-- section:jobs -->
## 定时任务

关注 Job / Scheduler 变更时：

- 调度频率、并发实例和失败重试。
- 补数、重跑和幂等。
- 与在线读写路径的数据一致性。

<!-- section:messaging -->
## 消息与异步

关注 Consumer / Listener / MQ 变更时：

- 消费幂等、顺序和重复投递。
- 死信、重试和积压处理。
- 生产端与消费端字段兼容。

<!-- section:test-design -->
## 测试点设计

每个测试点应包含：优先级、前置数据、操作、可观测预期结果和证据（`evidence_refs`）。

优先覆盖：

- 需求中的正常流程。
- 变更方法的新增分支和删除分支。
- 空值、边界值、重复请求和非法状态。
- 公共方法的已确认调用方回归。
- 数据库、事务、缓存、消息和外部服务异常。
- 旧数据和混合版本兼容性。

<!-- section:limits -->
## 限制

反射、动态代理、SPI、配置驱动、生成代码、SQL 动态拼接和跨仓库调用无法仅靠变更 AST 完全确认，必须列入待确认。
