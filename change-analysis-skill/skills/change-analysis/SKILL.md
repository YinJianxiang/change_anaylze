# 代码变更分析

## 执行 Skill

```powershell
$Skill = "D:/Project/change_analyze/change-analysis-skill"
& "$Skill/run.ps1" -RequirementUrl "<TAPD 或钉钉文档链接>" -Branch "<目标分支>" -Repo "<仓库绝对路径>" -BaseBranch "master" -Output "D:/Project/change_analyze/.local/change-analysis.json"
```

仅分析 patch 时使用 `--diff-file <patch>`；可用 `--preview` 查看采集计划。不要修改业务仓库。

## 唯一输出标准

开始分析前读取 `analysis_input.analysis_guidance` 中的完整指南和模板；旧输出缺少该字段时读取：

- `../../src/change_analysis_skill/guidance/impact-and-test-guide.md`
- `../../src/change_analysis_skill/guidance/report-template.md`

最终报告严格按模板顺序输出：分析范围、仓库上下文、改动与需求摘要、影响链路、调用链影响、风险结论、必测内容、回归范围、需求追踪（仅 Mode B）、建议执行、待确认与限制。沿用模板表头，不另起风险优先、公式专章或多层附录体系，不复制整段指南到报告。确有必要的技术细节放在相应章节，不用采集统计替代业务结论。

## 分析步骤

1. 有可用需求正文时采用 Mode B（需求对照）；仅代码或需求不可用时采用 Mode A，需求推断注明置信度。需求部分获取时注明未覆盖验收点，不宣称需求完整。
2. 固定 base、head、merge-base 及变更来源，检查 `selection_plan`、`impact_units`、`evidence_warnings`、`analysis_limits` 和摘要截断；需要时沿 `evidence_reference` 读取完整证据。
3. 阅读 diff 和相关源码，提炼有直接证据的原行为与新行为。删除的行为与新增的行为同等检查。Java AST 仅覆盖变更作用域，其他语言仍需源码审查。
4. 从变更对象定向追踪前端、接口、后端、数据和外部依赖，填写影响链路与调用链影响。即使只改一端也检查前后端契约；公共方法和组件检查消费者及相关测试，并注明置信度。
5. 文本引用和 Skill 的 `caller_candidates`、`symbol_references`、`api_references` 都不是已确认调用关系，必须读源码确认。区分直接影响、间接回归、兼容性、部署/数据；缺失仓库或动态调用列为限制，不伪造完整链路。
6. 按指南使用 High / Medium / Low 风险等级，依据实际影响、覆盖和回滚证据判断。规则扫描只提供候选，不等于缺陷；没有证据时写待确认，不把一般检查项包装成已确认问题。
7. 按“前置条件/数据 → 操作 → 可观察预期结果 — 证据”写必测内容，优先级与风险等级分开；用具体状态码、界面状态、落库值、事件、权限或回滚结果，避免“正常/正确/无问题”。按变更信号选择测试维度，不机械罗列全部类别。
8. 明确核心回归、定向回归，只有隔离证据充分时列可不回归。Mode B 逐项追踪验收点及疑似超范围实现；建议执行只列仓库实际存在的测试或命令，未执行写“未执行，仅建议”。

## 需求完整性核验（Mode B 必做）

有需求文档时必须双向分析：从代码检查行为与影响，也从需求逐项检查是否全部实现，不能只覆盖 diff 中出现的需求点。

1. 完整阅读可获取的需求正文、表格、关联文档及验收标准；图片/原型中有业务规则时一并核验，无法读取的内容明确列为缺口。将功能、字段、规则、权限、状态、异常、兼容及数据/配置要求拆成可独立判定的验收点，保留需求原文位置并编号；不得只摘本次已改的部分。
2. 对每个验收点，在固定的目标版本中定向查找实现，必要时读取 diff 之外的已有源码、前后端、数据脚本、配置和相关测试；与基准版本比较，区分本次新增、已有实现和本次删除/破坏。没有 diff 或搜索零命中不能直接证明未实现。Skill 采集仍限变更作用域，此处是助手按需求执行的补充定向检查，不是全仓库扫描。
3. 在“需求追踪”表逐项给出实现证据、测试证据/建议和状态：已实现、部分实现、未实现、实现与需求不一致、无法确认、不适用。已实现须有源码/配置证据；部分实现列明已覆盖与缺失分支；未实现须有预期承载位置及实际缺失证据，只有检索未发现时写无法确认；不适用必须有明确范围依据，不自行排除。
4. 每项未实现、部分实现或不一致都说明需求预期、目标版本实际行为、差距、业务影响及补充验证方法，并关联必测内容。关键仓库、原型、配置或业务口径缺失时标无法确认，说明需要什么证据，不冒充已确认缺陷。
5. 在“改动与需求摘要”汇总验收点总数及各状态数量，回答是否全部实现。有任何未核验内容就不能宣称全部实现；源码已实现不等于运行验证通过，执行状态另行说明。需求追踪完整覆盖每个已识别验收点，未读取需求内容另列限制，最后再反向检查疑似超范围实现。

## 数据库只读取证（按需）

涉及表结构、SQL、历史数据、计算口径或需求落库结果时，可用 Skill 内部数据库工具补证；不是第二个 Skill，普通代码采集不会自动连接数据库。

```powershell
# 从工具项目根目录执行；仅首次需要安装可选依赖。
& ./.venv/Scripts/python.exe -m pip install -e './change-analysis-skill[database]'
& ./.venv/Scripts/python.exe -m change_analysis_skill.database_cli --env-file .env --sql "SELECT 1 AS connected"
# 业务查询优先使用已核实表名、明确列和参数化条件，复杂 SQL 写入本地文件。
& ./.venv/Scripts/python.exe -m change_analysis_skill.database_cli --env-file .env --sql-file .local/evidence.sql --params '[123]' --max-rows 100 --timeout 10 --output .local/database-evidence.json
```

- 使用 `DATABASE_URL` 或 `DB_HOST/DB_PORT/DB_USER/DB_PASSWORD/DB_NAME`，不得在报告、命令行参数或日志中写凭据。SQL 参数使用 `%s` 占位符，不能用字符串拼接外部输入。
- 只允许单条只读查询；禁止修改数据、建表、迁移、执行存储过程、导出文件和锁定操作。使用专用最小权限只读账号；词法检查和只读事务不能替代数据库权限，不调用未知存储函数。
- 先从源码确认表和字段，再按需求定向读取；优先元数据、计数和脱敏聚合，避免大范围 `SELECT *` 和敏感明细。结果有行数上限，截断不能推断全量分布。
- 记录查询目的、SQL 文件/查询依据、脱敏参数、环境/库的逻辑名称、执行时间、截断和结果证据；数据库样本不是代码实现完整性证明，也不能视为固定代码提交对应的数据快照。缺少环境/版本/口径对应关系时明确限制。
- 数据库结果只补充“实现证据”“数据/外部依赖”“必测内容”和“待确认与限制”等现有章节，不另建报告体系。连接失败如实披露，不改用写操作或绕过只读保护。

## 证据边界

- 模板中的仓库上下文字段必须按事实填写；保留实际的 `Changed-scope AST evidence analysis` / `Partial evidence analysis` / `Diff-only evidence analysis`，不得将定向搜索改称全仓库分析。
- 完整调用链搜索、全项目源码扫描、调用图计数未采集时写“否”或“未采集”，不以候选数充当调用边数。
- 仅 patch 或未获取完整仓库时明确写：`未获取完整仓库，无法确认所有间接调用方和完整回归范围。`
- 影响结论和测试点给文件行号或作用域等证据锚点，区分源码确认、推断与运行验证。未运行不写通过。
- Skill 自动 Markdown 是同模板的证据草稿，不是最终业务结论。当前助手必须补充源码判断与可执行场景，不得将“待分析”直接当作完成报告。
- 不重新构建全仓库通用调用图，不调用 OpenAI API、`llm_server` 或 Agent SDK。
